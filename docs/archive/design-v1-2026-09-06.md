# Descent — Design & Technical Document

**Working title:** Descent
**Genre:** Single-player 3D extraction dungeon crawler with roguelite meta-progression
**Status:** Pre-production design document
**Constraint:** All code and assets to be produced primarily by an LLM coding harness

---

## 0. Development tenets

**These are not guidelines. They are the constitution of this project.** Every decision below is downstream of them. When a tenet conflicts with speed, convenience, or elegance, the tenet wins.

### Tenet 1 — Readable, simple, optimised code beats clever code, every time

Even if it is more lines. Even if it looks naive.

- Explicit over implicit. A junior reader — or a fresh model with no context — must understand a function from the function alone.
- No speculative abstraction. Do not build for a use case that does not exist yet.
- No clever one-liners. If it needs a comment to explain *what* it does, rewrite it. Comments explain *why*, never *what*.
- Optimise on measurement, never on instinct. Profile first, then optimise, then document the measurement in the decision log.
- Long, obvious, flat code is correct. Short, dense, layered code is a liability.

### Tenet 2 — Zero silent failures

**Any and all issues must be reproducible, examinable, and fixable.** A bug we cannot reproduce is a bug we cannot fix.

- No empty `catch` blocks. Ever.
- No default fallback values that mask a missing or malformed input. Missing data is an error, not a zero.
- Fail loud, fail early, fail with context.
- Every error carries the run seed, floor number, tick number, and entity IDs. Enough to replay it exactly.
- Assertions are on in development builds and validate every invariant we believe to be true.
- Structured logging, not `print`. Logs are machine-parseable by default, because Tier 3b (§8) reads them.

### Tenet 3 — Everything must be tested

No code merges without tests. No exceptions for "trivial" changes.

- Every system in `Descent.Core` has unit tests.
- Every procedural generator has property tests over large seed sweeps.
- Every gameplay change is exercised by the bot harness before merge.
- A bug fix without a regression test that fails on the old code is not a fix.

### Tenet 4 — All PRs reviewed by a different model before merge

The model that writes the code does not approve the code.

- Cross-model review is mandatory and blocking.
- The reviewer's job is to find what the author rationalised: silent failures, untested branches, unnecessary complexity, tenet violations.
- Review findings are recorded, not just resolved in conversation.
- See §11 for the full gate.

### Tenet 5 — Document everything, always

**This is the single most important duty in the project.**

Continuity of development work matters more than any individual feature, because every session begins with a model that has no memory of the last one. Undocumented context is destroyed context.

Every change updates: the decision log, the open-questions register, the roadmap, and the session handoff document. See §11 for the required artifacts and their formats.

**A PR that changes behaviour without updating documentation is incomplete and must not merge.**

## 1. Concept

A single-player third-person dungeon crawler. You descend into a procedurally generated dungeon, one floor at a time, and every floor ends in a boss. The deeper you go, the better the rewards — but you only keep your gear if you choose to **ascend**. Die, and the loot is gone.

**Core loop:** clear floor → beat boss → look at your loot → decide whether to descend again or ascend.

The dungeon is content. The *decision* is the game.

### Boss cadence

| Floor interval | Encounter type |
|---|---|
| Every floor | Boss |
| Every 5th floor | Mega-boss |
| Every 15th floor | Ultra-boss |

### Pillars

1. **Voluntary greed.** The player, not the designer, sets the difficulty ceiling of each run.
2. **Real loss.** Death costs the run's gear entirely. Stakes are the product.
3. **Nobody to blame.** Solo means the descend/ascend call is pure self-knowledge — no party to talk you into it, no one else to fault when it goes wrong.
4. **Weapons with weight.** Projectiles are real objects that travel, drop, and can miss. Skill expresses through aim and timing, not stat checks.
5. **Readable at a glance.** Blocky art and clear silhouettes so combat parses instantly at gameplay camera distance.

## 2. Combat, gear & progression

> **⚠ PROVISIONAL.** Everything in this section is a starting concept, not a commitment. It exists to give implementation something concrete to build against and is expected to change substantially during prototyping. Changes here are cheap and encouraged. Record every one in the decision log (§11).

### 2.1 Two-track economy

The critical structural decision: **loot and skill points are separate currencies with different loss rules.**

| Track | On ascension | On death |
|---|---|---|
| **Gear / loot** | Kept in full | **Lost entirely** |
| **Skill points** | Kept in full | **Kept at a reduced rate** |

This directly addresses the retention problem flagged in §4.1. Hades grants meta-currency even on failed runs precisely because pure total loss suppresses replay. A failed run here still moves the skill tree forward, just inefficiently — so a death is a bad trade, not a wasted evening.

**The reduction rate is the single most sensitive number in the game.** See §4.3.

### 2.2 Weapon classes

Gear spans melee and projectile weapons. Provisional families:

| Class | Examples | Character |
|---|---|---|
| **Melee** | Swords, axes, hammers, spears | Reach, swing arc, commitment on windup |
| **Bows** | Shortbow, longbow, crossbow | Arc, draw time, travel time, gravity |
| **Guns** | Pistols, rifles, shotguns, heavy | High velocity, flat trajectory, ammo-constrained |
| **Thrown / exotic** | Bombs, chakrams, magic bolts | Slow, arcing, area effects |

Design intent is that these coexist rather than tier up. A slow heavy bolt and a fast rifle round should be different tools, not upgrade steps.

### 2.3 Projectiles are physical. No hitscan.

**This is a hard requirement, not a preference.**

- Every projectile is a simulated object with a position and velocity, advanced each tick.
- **Travel time is real.** Fast rounds cross a room in a few ticks; slow bolts take a second or more. Leading a moving target is a skill.
- **Gravity applies to arcing weapons.** Arrows drop. Range is finite and falls out of the arc naturally, not from an arbitrary distance cap.
- **No infinite-range shots.** Projectiles despawn on a lifetime or distance budget, and that budget is a weapon stat.
- Projectiles can be blocked by geometry, and ideally by other entities.

### 2.4 Skill tree

Skill points earned per run, spent between runs on a persistent tree.

- Nodes upgrade abilities, weapon-class proficiencies, and utility.
- Provisional shape: several shallow branches over one deep tree, so early builds diverge quickly.
- Respec policy is an open question (§4.3).

### 2.5 Ammunition — undecided

Guns may or may not consume ammo. This is not a small question, because ammo scarcity is one of the strongest available pressure levers on the descend/ascend decision.

| Model | Effect on core loop |
|---|---|
| No ammo | Guns become strictly dominant over bows; simplest to build |
| Ammo as loot | Scarcity creates real pressure to ascend; risks dead runs where the player is disarmed and helpless |
| Ammo regenerates slowly | Softer pressure, harder to reason about |
| Ammo per weapon type | Deepest, most inventory management, most UI |

Bows would need a parallel answer — infinite arrows, or recoverable ones.

**Recommendation:** prototype with no ammo first to tune projectile feel in isolation, then layer scarcity in as a separate, reversible experiment.

## 3. Positioning

### Not Minecraft Dungeons

Superficially adjacent, structurally different:

| | Minecraft Dungeons | Descent |
|---|---|---|
| Camera | Fixed isometric | Third-person, player-controlled |
| Combat | Positional, Diablo-like | Aimed, physical projectiles, dodging |
| Structure | Mission map, authored levels, fixed order | One continuous procedural descent |
| Death | Lives system, revives, loot retained | Loot lost entirely; skill points reduced |
| Progression | Gear + enchantments, kept always | Persistent skill tree + gear gated on ascension |

### Actual neighbours

- **Hades** — the roguelite meta-progression benchmark, and the closest structural sibling
- **Risk of Rain 2 (solo)** — third-person procedural with escalating stages
- **Dark and Darker** — extraction dungeon crawling, but PvPvE
- **Spelunky** — solo, total loss, mastery-driven
- **Deep Rock Galactic** — the reference for physical, non-hitscan weapon feel

### The positioning risk

Extraction as a genre is overwhelmingly multiplayer, and a large share of its tension comes from *other people*: the greed of your squad, the fear of another player, the negotiation over when to leave. Going single-player removes all of it.

**That tension now has to come entirely from the dungeon and the economy.** §4.2 is the main lever available for it.

## 4. Open design questions

Unresolved. Each must be answered before the systems they touch are implemented. All live in the open-questions register (§11).

### 4.1 Run length vs. loot loss

Tarkov raids run 30–40 minutes, which is precisely why total loss is tolerable there. If reaching floor 15 takes three hours and the player dies on floor 14, the design may produce quitting rather than replaying.

**Partially resolved** by the two-track economy (§2.1) — skill points survive, so a failed run is never fully wasted.

**Still open:**
- Frequent ascension points, so greed is incremental rather than one enormous bet
- Partial gear banking at mega-boss checkpoints (floors 5, 10, 15…)

**Recommendation:** make the gamble incremental. "One more floor?" is a richer question asked twenty times per run than once.

### 4.2 What does ascending cost?

**The most important open question in the design.** With no other players supplying tension, the ascent itself has to carry weight. If ascending is a free instant button, optimal play is to bank constantly and the greed decision evaporates.

| Model | Effect |
|---|---|
| Instant and free | No tension. Rejected. |
| Costs a consumable | Turns ascension into an inventory decision |
| Fight back up *n* floors | Ascending becomes a run in itself; strong tension, high build cost |
| Timed ascent, dungeon reacts | Escalating pressure; a natural climax to each run |
| Ascension points at fixed floors only | Simple, readable, forces commitment in blocks |
| Cost scales with depth | Deep runs get progressively harder to cash out |

**Recommendation to prototype first:** ascension points at fixed floors, with a timed and increasingly hostile ascent. Per-run climax, cheap to build, combines cleanly with §4.1.

### 4.3 The skill point death penalty rate

**A tuning number with an exploit attached.** If the retained rate is too generous, deliberate death becomes optimal: farm three easy floors, suicide, skip the ascent cost entirely, repeat. That is a faster points-per-hour loop than playing well.

Constraints the number must satisfy:
- Ascending must always beat dying, in points per hour, at every depth
- The gap must widen with depth, so greed is rewarded
- The floor cannot be zero, or Tenet-adjacent retention problems return

**This is exactly the class of exploit Tier 3 LLM play (§8) exists to find.** Instrument points-per-hour by strategy from the first playable build.

### 4.4 Ammunition model

See §2.5.

### 4.5 Respec policy

Free, costly, or forbidden? Interacts with build diversity and with how punishing a mis-spent tree feels.

## 5. Technology stack

### 5.1 Engine: Godot 4 with C#

Chosen for harness-compatibility reasons rather than raw capability.

- **Text-based scenes.** `.tscn` and `.tres` are plain text. A harness can read, diff, and write them. Unity's YAML+GUID prefabs and Unreal's binary Blueprints are effectively write-only for an LLM.
- **A compiler.** Static typing is the single most valuable feedback signal in an autonomous loop — a precise error the harness can fix without a human. GDScript lets bad code reach runtime, and most GDScript in training data targets Godot 3.x, causing constant API hallucination against 4.x.
- **Headless mode.** `godot --headless` runs in CI, so the harness can test what it wrote.
- Small binary, permissive license, fast iteration.

### 5.2 Alternatives considered

| Option | Verdict |
|---|---|
| **Bevy (Rust)** | Philosophically ideal — everything is code, nothing is binary — but API churn plus lagging training data means constant hallucinated APIs |
| **Unity** | Deepest training corpus and best asset ecosystem, but editor-centric workflow fights automation. Only viable if all scenes are built procedurally at runtime |
| **Unreal** | Binary assets are disqualifying for this constraint |

### 5.3 Platform targets

**Windows, Linux, and macOS (Apple Silicon + Intel). All fully supported.**

Since Godot 4.2, C# projects support all desktop platforms. macOS builds ship as universal binaries covering arm64 and x86_64. Exports bundle the .NET runtime, so players install nothing. Web is the only unsupported C# target and is not in scope.

**Rendering on macOS:** Godot 4.4 added a native Metal backend, now the default driver on Apple Silicon, replacing the MoltenVK Vulkan-over-Metal translation layer. It is at least as fast as the Vulkan path and often faster. Intel Macs continue on MoltenVK.

**Platform friction, in order of annoyance:**

| Issue | Detail |
|---|---|
| **macOS notarization** | Gatekeeper blocks unsigned apps. Requires an Apple Developer account (~$99/yr). Signable and notarizable from Linux via `rcodesign` if a Mac is not in the build loop |
| **Linux path case-sensitivity** | Classic "works on Windows, breaks on Linux" bug. The `.bbmodel` loader is the likely offender. **Asset QA gate must check filename casing** (§8) |
| **Save paths** | Always use Godot's `user://`. Never hardcode a path |
| **Shader compilation stutter** | Pre-warm shaders at load. Worst case is a cleared shader cache on first launch |

### 5.4 Cross-platform determinism — a hard constraint

**Tenet 2 depends on this, and it is not free.**

IEEE basic operations — add, subtract, multiply, divide, sqrt — are bit-identical across platforms and architectures. **Transcendentals are not.** `Math.Sin`, `Cos`, `Atan2`, `Pow` and friends delegate to the platform's libm, which differs between Windows, Linux, and macOS, and between x86-64 and ARM64.

**The failure this causes:** a player on macOS sends a seed and intent stream. It is replayed on x64 CI. The arrow lands somewhere slightly different. The bug is not reproducible, and Tenet 2 is broken in exactly the case it exists to cover.

**The fix — implement early, retrofitting is far worse:**

- A `DetMath` class in `Descent.Core` implementing `Sin`, `Cos`, `Atan2`, `Sqrt` and friends from polynomial approximations using **only** basic IEEE operations. Simple, readable, table-driven, unit-testable — squarely Tenet 1.
- A **lint rule forbidding `System.Math` transcendentals anywhere in `Descent.Core`.** Enforced at the PR gate (§11.5).
- **No `Vector<T>`, no SIMD intrinsics, no parallel reductions in Core.** Vector width differs between AVX2 and NEON, which changes summation order and therefore results.
- A CI job that runs an identical seed on Linux x64 and macOS arm64 and **asserts bit-identical end state.** This is the test that proves the property holds.

Cross-platform determinism is not required for single-player gameplay. It is required for reproducible bug reports, for CI results matching what players experience, and for any future seed sharing or daily challenge.

### 5.5 Development environment

**Primary development machine: Mac Mini, base M4 (10-core CPU, 10-core GPU, 16 GB unified memory, 256 GB SSD).**
**Secondary test machine: Windows 11, i5-12500 + GTX 1660 Super.**

This is a strong pairing. Developing on ARM64 macOS while shipping to x86-64 Windows means the **unusual architecture is the daily driver**, so portability and determinism divergence surface continuously rather than at launch. The Windows box doubles as the low-end target and a real second-architecture determinism check.

**Known constraints of the base M4 Mac Mini:**

- **256 GB SSD is the real pinch.** Godot + .NET SDK + Xcode command line tools + git history + build artifacts + bot-harness run logs add up fast. **Plan on an external SSD for the project directory and log archives.**
- 16 GB unified memory is ample for the game and adequate for the toolchain. It will feel tighter running the editor, an IDE, and a large bot sweep simultaneously.
- The 4P/6E core split serves the Tier 2 bot harness well; .NET on ARM64 is mature and fast.

## 6. Art direction

### 6.1 Minecraft-style cuboid models — a technical decision, not just aesthetic

This choice removes the majority of AI asset-pipeline risk.

Industry assessments of AI 3D generation consistently identify the weakest categories as **deforming hero characters, dimensionally exact parts, and reusable modular kits** — almost exactly the asset list a dungeon crawler needs. Cuboid models sidestep all of it:

- A model is a hierarchy of boxes: origin, size, pivot, rotation, UV offset. **That is a JSON file.** An LLM writes it deterministically and can verify it by parsing it back.
- **No topology.** No edge loops to get wrong, because nothing deforms. Limbs are rigid boxes parented to bones.
- **No skinning weights, no extreme-pose failure.**

### 6.2 Format and pipeline

**Blender is removed from the pipeline entirely.**

- Author in **Blockbench `.bbmodel`** — documented JSON, with a free editor for human inspection and hand-fixes
- Godot loader builds an `ArrayMesh` directly from the box list
- No glTF/FBX export, no MCP bridge, no round-trip import testing, no engine-contract failures

### 6.3 Animation as code

- **Locomotion:** procedural. Limb rotation as a function of distance travelled.
- **Attacks and abilities:** short authored keyframe lists of per-bone euler rotations.
- **Weapon animations carry the combat read.** Melee windups must telegraph. Bow draws must show draw strength. These are the frames that matter most.
- Style target: snappy, exaggerated, low frame count.

### 6.4 Projectile readability

With a large weapon roster and no hitscan, **every projectile must be visually distinct in flight.** Speed, trail, colour, and size all encode what is coming at you. This is a gameplay requirement dressed as an art requirement, and it is a Tier 4 test target (§8).

### 6.5 Textures

Pixel atlases (16×16 or 64×64) emitted by a Python generator from a **locked palette of ~32 colours**. The harness iterates on the generator, not on individual images, so style consistency is structural rather than supervised.

### 6.6 The real art risk

Blocky art looks good because of palette discipline, silhouette readability, and lighting — not because boxes are easy to model. The failure mode for generated voxel art is fifty enemies that all read as "vaguely humanoid brown thing" at gameplay distance. **Weapons have the same failure mode**, and a large roster makes it worse.

**Mitigations (enforced as harness constraints):**
- Fixed palette, no exceptions
- Each enemy family and each weapon class assigned a distinct silhouette proportion, specified before generation
- Rendered contact sheets reviewed **at actual game zoom**, never in isolation
- One texture atlas, one material — this also collapses draw calls

### 6.7 Performance

Single atlas + aggressive instancing + greedy meshing on static dungeon geometry. Procedural floors become cheap enough to be generous with dungeon size.

**Both target machines are heavily overpowered for this content.** Raw throughput is not the risk. **Hitches are.** The performance work that matters:

| Concern | Severity | Mitigation |
|---|---|---|
| Floor-transition freeze (procgen + greedy mesh + GPU upload) | **The main risk** | Generate the next floor on a background thread during the current floor. `Descent.Core` is pure C# and threads trivially |
| Greedy meshing skipped or broken | Critical | Naive per-cube rendering explodes draw calls and tanks both machines. Assert mesh counts in tests |
| Shader compilation stutter on first encounter | Medium | Pre-warm all shaders at load |
| Projectile broadphase at high counts | Low | Fine at hundreds. Profile before optimising (§9.3) |

**Target:** locked frame time with zero hitches over a 15-floor run, measured as 99th-percentile frame time, not average FPS. Average FPS will look excellent and tell you nothing.

## 7. Architecture

### 7.1 Core/engine split

Two layers, strictly separated:

**`Descent.Core`** — a pure C# class library with **zero engine dependencies**:
- Procedural generation
- Combat math and **projectile simulation**
- Loot tables and weapon stats
- Skill tree and point economy
- Floor scaling and difficulty budgets
- Ascension economy

**`Descent.Game`** — a thin Godot layer that renders and inputs.

The core unit-tests in milliseconds via `dotnet test`, so the harness iterates on actual game design without launching an engine.

### 7.2 Determinism

Non-negotiable:
- Seeded RNG throughout
- Fixed timestep
- No reliance on frame time in simulation
- **`DetMath` only — no `System.Math` transcendentals, no SIMD, in `Descent.Core` (§5.4)**

**Consequence:** `seed + intent stream` is a complete replay. A bot dying strangely on floor 9 is reproducible exactly — which is Tenet 2 made structural.

### 7.3 Projectile simulation — a determinism constraint

**Godot's physics engine is not deterministic and must not be used for projectiles.**

Projectiles are simulated in `Descent.Core` with a purpose-built integrator:

- Fixed-timestep Euler or Verlet integration. Simple, readable, deterministic (Tenet 1).
- **Swept collision, not point tests.** A fast round moving further than a wall is thick will tunnel through it under naive per-tick position checks. Raycast the segment travelled each tick.
- Godot's `RigidBody` exists for cosmetics only — never for anything the simulation reads.
- Projectile counts stay low enough that a flat array and brute-force broadphase is sufficient. Do not build spatial partitioning until profiling demands it (Tenet 1).
- **Trajectory and aiming math uses `DetMath`, never `System.Math` (§5.4).** Arc solvers are the most trig-heavy code in the project and the most likely source of cross-platform divergence.

**Property test targets (§8):** no tunnelling at maximum velocity through minimum wall thickness; arcing solver reaches a reachable target; every projectile terminates within its lifetime budget.

### 7.4 Data-driven content

Enemies, items, weapons, projectile definitions, room templates, boss patterns, and skill tree nodes live in JSON or `.tres` resources — not code. Generating content *data* is the cheapest and most reliable thing an LLM does, and it keeps the code surface small and readable.

**Weapon stats are pure data**: damage, velocity, gravity scale, lifetime, spread, windup, recovery, ammo cost. Adding a weapon must never require code.

### 7.5 Persistence

No networking. No authority model. But save integrity still matters, and the failure mode is corruption, not cheating.

- Three stores: **skill tree** (durable), **banked gear** (durable), **run state** (volatile)
- Run state commits to durable stores **only on successful ascent**, except skill points, which commit at the reduced rate on death
- **Atomic writes** — write to temp, fsync, rename. A crash mid-write must never destroy banked progress
- Decide explicitly: does a mid-run crash count as a death? Silent auto-resume undermines the stakes; hard loss on a crash the player did not cause is worse. Recommended: crash-resume permitted once per run, logged
- Save tampering is out of scope. A solo player editing their own save is only cheating themselves

## 8. Testing strategy

Four tiers, ordered by cost. Tenet 3 makes all of them mandatory, not optional.

### Tier 1 — Property tests (no agent, highest value)

**Procgen**, across 100,000 seeds:
- Every room reachable from spawn
- Boss room exists and is correctly gated
- No room overlaps
- Difficulty budget within tolerance for the floor number
- Ascension point always reachable

**Projectiles**, across the full weapon roster:
- No tunnelling at max velocity through min wall thickness
- All projectiles terminate within lifetime budget
- Arc solver reaches reachable targets and reports failure on unreachable ones

**Economy**:
- Skill point totals never go negative or overflow
- Ascending beats dying in points-per-hour at every depth (§4.3)

**Cross-platform determinism**:
- The same seed run on Linux x64 and macOS arm64 produces a **bit-identical end state** (§5.4)
- This job runs on every PR. A divergence blocks merge.

### Tier 2 — Scripted bots (volume)

Ten thousand runs overnight in headless `Descent.Core` at 100× speed. No rendering, no tokens. Catches crashes, softlocks, unreachable geometry, and infinite loops. **Most of what needs testing lives here.**

### Tier 3 — LLM play (exploration)

Game state exposed as compact JSON over a socket. The model acts at **1–5 decisions per second, never per frame.**

Its value is trying what scripted bots will not:
- Suicide-farming to beat the ascent cost (§4.3)
- Refusing all skill points, or dumping everything into one branch
- Melee-only and ranged-only runs
- Ascending on floor 1 every time
- Hoarding ammo, or wasting it deliberately

This is how degenerate builds and economy exploits surface.

### Tier 3b — LLM as log reader

Often a better use of tokens than play. Cheap bots generate structured run logs; the harness aggregates and hands the model the outliers:

> "Here are the 40 runs that ended in under 90 seconds. What do they share?"

Tenet 2's structured logging exists to make this tier cheap.

### Tier 4 — Vision-based play (sparingly, late)

The only tier that catches camera clipping, unreadable enemy telegraphs, **indistinguishable projectiles in flight**, and UI occluding the fight. Expensive; run against the actual rendered build near milestones.

### Asset QA gate

Automated, scriptable, pass/fail: polygon budget, watertightness, scale and pivot placement, UV coverage, survives a test rig at extreme poses, **and filename casing matches references exactly** (Linux is case-sensitive, §5.3).

### What automation cannot tell you

Automated play will confirm the ascension gamble is *reachable*. It will not tell you whether descending one more floor ever felt **agonising**, or whether a bow feels good to fire — and the design rests on both.

**Budget for human playtests specifically on those questions.** Nothing else substitutes.

## 9. Engineering standards

The operational form of Tenets 1 and 2.

### 9.1 Code

- Explicit types. No `var` where the type is not obvious from the right-hand side.
- Functions do one thing. If the name needs "and", split it.
- No inheritance hierarchies deeper than one level without a documented reason.
- No reflection, no dynamic dispatch, no runtime code generation in `Descent.Core`.
- **No `System.Math` transcendentals, no `Vector<T>`, no SIMD intrinsics in `Descent.Core`.** Use `DetMath` (§5.4). Enforced by lint at the PR gate.
- Public API surface is documented; internals are self-evident or rewritten.
- Dependencies are a cost. Every added package requires a decision-log entry justifying it.

### 9.2 Failure handling

- Every `catch` either handles meaningfully or rethrows with added context. Nothing else.
- No `null` returns for "not found" — use an explicit result type or throw.
- Invariant violations throw in development, log-and-continue only where the alternative is a crash mid-session, and always with a full context dump.
- Every log line carries: timestamp, seed, floor, tick, subsystem.
- **Crash reports include the seed and intent stream**, making every crash replayable (§7.2).

### 9.3 Performance

- No optimisation without a profile.
- Every optimisation records its before/after measurement in the decision log.
- An optimisation that reduces readability requires an explicit, documented tradeoff decision.

## 10. Build order

1. `Descent.Core` skeleton + deterministic seeded RNG
2. **Documentation artifacts and PR gate established (§11) — before any feature code**
3. **`DetMath` + the cross-platform determinism CI job (§5.4) — before any simulation math is written**
4. Procgen + Tier 1 property tests *(before any rendering exists)*
5. Intent layer and simulation loop
6. Projectile simulation + swept collision + Tier 1 projectile tests
7. Scripted bot harness (Tier 2)
8. Minimal Godot rendering layer, `.bbmodel` loader
9. **Background floor generation from the start** — retrofitting threading later is painful (§6.7)
10. Melee combat, one enemy family, one boss
11. Ranged weapons: one bow, one gun. Tune feel before adding roster breadth
12. **Resolve §4.1 and §4.2**, then implement ascension and gear banking
13. Skill tree and point economy. **Resolve §4.3** and instrument points-per-hour immediately
14. Persistence and atomic save writes
15. Windows + Linux export pipeline and macOS notarisation set up **before** content expansion
16. Content expansion via data files, LLM play (Tier 3) in the loop

## 11. Documentation & continuity protocol

**Tenet 5, operationalised. This section is the most important in the document.**

Every session starts with a model that remembers nothing. The repository is the only memory. Anything not written down did not happen.

### 11.1 Required artifacts

| File | Purpose | Update cadence |
|---|---|---|
| `DESIGN.md` | This document. Current state of intent | On any design change |
| `DECISIONS.md` | Append-only decision log. Every choice, its alternatives, its rationale, its date | On every decision |
| `QUESTIONS.md` | Open questions awaiting an owner decision, with options and tradeoffs laid out | On raise and on resolve |
| `ROADMAP.md` | Ordered plan, current milestone, what is done and what is next | On any scope or order change |
| `HANDOFF.md` | Session handoff. Rewritten at the end of every session | Every session, without exception |

### 11.2 Decision log entries

Each entry records:
- **What** was decided
- **What alternatives** were considered and why they lost
- **What it affects** — which sections, systems, files
- **Reversibility** — cheap to undo, or load-bearing
- **Date and session**

A decision that is later reversed is never deleted. Append the reversal and its reasoning. The history is the value.

### 11.3 Owner questions

Questions requiring a human decision go in `QUESTIONS.md` with:
- The question stated plainly
- Options with concrete tradeoffs
- A recommendation and its reasoning
- **What is blocked** until it is answered

Do not silently pick a default and proceed. Ask, record, and if unblocking is necessary, implement behind a flag and record that too.

### 11.4 Session handoff

`HANDOFF.md` is rewritten at the end of every session and must let a fresh model resume cold. Minimum contents:

- What was done this session, and why
- **Current state of the build** — what runs, what is broken
- What is in flight and half-finished, with file paths
- **Traps and gotchas discovered** — the things that cost time to learn
- Open questions blocking progress
- The next concrete action, specific enough to start immediately

### 11.5 The PR gate

No merge without all of the following:

- [ ] Tests written and passing (Tenet 3)
- [ ] No silent failures introduced; errors carry full context (Tenet 2)

## 13. Summary of key decisions

- **The five tenets in §0 outrank everything else in this document**
- **Documentation and continuity are the highest-priority engineering work**, not overhead
- **Single-player only.** No netcode, no authority model, no session management
- **Godot 4 + C#** — text scenes, a compiler, headless CI
- **Cuboid/Blockbench models** — eliminates the entire AI-asset weak zone
- **No Blender in the pipeline** — fewer places for an autonomous loop to fail silently
- **Pure-C# core, thin engine layer** — millisecond design iteration
- **Projectiles are physical and simulated in Core** — no hitscan, no engine physics, swept collision
- **Two-track economy** — loot lost on death, skill points reduced. The reduction rate is the most sensitive number in the game
- **Windows, Linux, macOS (Apple Silicon).** All fully supported; native Metal on Apple Silicon; web out of scope
- **`DetMath`, not `System.Math`, in Core** — platform libm divergence would otherwise break Tenet 2
- **Determinism + intent layer** — replays and agent testing, and the structural guarantee behind Tenet 2
- **The performance risk is hitches, not throughput.** Both target machines are overpowered for this content
- **Property tests > scripted bots > LLM play** — token cost ordered against value
- **The design risk is the economy, not the technology.** Specifically: what ascending costs, and what dying refunds
