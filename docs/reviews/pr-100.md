## Findings

### P1-1: The build-failure record drops carried seeds

Status: fixed in `b07e6ed828d1d81f430798480bd698df3f47671a`.

Open at: `198a0c9d5b6c90d41042dd58b02f597db240263f`.

File: `.github/scripts/night-failure-record.sh:14-17`.

Trigger: a night on `main` fails before `night-record` writes `night.json`, such as when the build fails and seed planning does not run.

Expected: D-567 requires each later night on `main` to run failed seeds until a night passes them. D-569 requires a promotion to prove that it ran each such seed.

Actual: the earlier fallback wrote only `commit`, `endedAt`, and `status`. The new script writes the failure record with `jq` and retains `failedSeeds` from the fetched record of `main`.

Consequence: the carried failure remains in the next plan and promotion check after a build failure.

Correction: `.github/workflows/night.yml` fetches the record of `main` in the fallback path and calls the script. The script fails on unreadable input, so the publish step does not replace the record with an empty carry.

Regression check: `dotnet test WhatYouCarry.slnx --filter FullyQualifiedName~TheFailureRecordOfABrokenBuildKeepsTheCarriedSeeds -v normal` passed the test on this checkout. It verified the carried seed in the failure record, the next seed plan, the promotion rejection when that seed did not run, absent input, and a wrong argument count. CI also passed after the fix.
