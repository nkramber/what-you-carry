## Findings

### P1-1: A malformed closed finding status passes as known

Status: fixed in `f280b72`.

Open at: `4029e36f62e4c072db3f47d7a1fa0327600f8e81`.

File: `WhatYouCarry.Tools/CodexReview/ReviewFindings.cs:120-125`.

Trigger: A review record has `Status: fixed.` or `Status: fixed without evidence.` for a P0 to P2 finding.

Expected: The parser rejects every status outside the forms in `findings.md`. A fixed status names its fixing revision, an accepted risk names a decision, and withdrawn is exact (F-125, T-2, D-514).

Actual: `IsKnownStatus` accepts any string that starts with a known word. `ReviewFinding.IsOpen` then reads `fixed.` as closed, so the review outcome can approve the record without a fixing revision.

Consequence: A malformed review record can pass the required review gate with an unresolved finding.

Correction: Parse each complete status form and reject a closed status without its required revision or decision id.

Regression check: Add review-record cases for `fixed.` and `fixed without evidence.`. `ReviewFindings.Parse` must reject both, and must still accept the documented fixed, accepted-risk, withdrawn, and open forms.

### P1-2: Fence parsing can expose a fake approving section

Status: fixed in `0d219b1`.

Open at: `4029e36f62e4c072db3f47d7a1fa0327600f8e81`.

File: `WhatYouCarry.Tools/ReviewGate/ReviewRecord.cs:150-160`.

Trigger: A valid triple-backtick code block contains two lines that start with `~~~`, then a sample `- Head` and `## Verdict` with an approving value.

Expected: The parser skips all text inside a fenced block, including lines that resemble another fence marker. The real Identity and Verdict sections alone determine approval (F-116, D-179, D-269).

Actual: `LinesOutsideFences` toggles its state for any line that starts with three backticks or three tildes. Markdown closes a fence only with the matching marker. The two tilde lines expose the sample sections, and `FindHead` and `FindVerdict` read their first matching values.

Consequence: An example inside a valid fenced block can supply the effective head and `Ready for owner merge`, despite a different real verdict.

Correction: Track the opening fence character and length. Close a block only on a valid matching fence.

Regression check: Add review-gate tests with a triple-backtick fence that contains tilde lines and fake Identity and Verdict sections. The fake sections must not affect the parsed real record.

### P1-3: A backtick in a fence info string can expose a fake approval

Status: fixed in `d027fa8`.

Open at: `d9c641328505ab67a4461e6292d845477488d61e`.

File: `WhatYouCarry.Tools/ReviewGate/ReviewRecord.cs:161-167`.

Trigger: A record starts a line with three backticks, text, and another backtick, such as `````c` ``. It then gives a real `Blocked` verdict, a line with three backticks, a fake `Ready for owner merge` verdict, and a final line with three backticks.

Expected: A backtick fence opener has no backtick in its info string. The parser and Markdown view must read the same Identity and Verdict sections (F-116, D-179, D-269).

Actual: `FenceRun` accepts the first line as an opener. `LinesOutsideFences` then treats the next triple-backtick line as its closer and reads the fake approval. [CommonMark section 4.5](https://spec.commonmark.org/spec/#fenced-code-blocks) rejects that opener because its info string contains a backtick, so the view treats the later triple-backtick line as the opener and hides the fake approval.

Consequence: The review gate can approve a record whose visible verdict is `Blocked`.

Correction: Reject a backtick fence opener when its info string contains a backtick.

Regression check: `ReviewGateRulesTests.ReviewGateOpensNoFenceOnABacktickInTheInfoString` covers the trigger and a valid info string. Both cases passed on effective head `5e43e89`.

### P2-1: A const text in another file can bypass the string lint

Status: fixed in `d027fa8`.

Open at: `d9c641328505ab67a4461e6292d845477488d61e`.

File: `WhatYouCarry.Tools/DetLint/GameStringScan.cs:186-204`.

Trigger: One Game file declares `public const string Died = "You died"`. Another file assigns `label.Text = Texts.Died`.

Expected: The string lint reports text that reaches a visible text member outside the string table (G-8, D-98, F-132).

Actual: `Run` scans each file with `ScanText`. `ConstStringNames` sees only fields in the current syntax tree. The const literal is exempt at its declaration, and the use in the second file does not match its file-local name set.

Consequence: The Game build can pass a player-visible string that has no string-table id.

Correction: Resolve const string symbols across the Game source before the per-file scan.

Regression check: `GameStringScanTests.AConstOfAnotherFileThatReachesATextIsAFinding` checks the cross-file text and a string-table id. It passed on effective head `5e43e89`.
